. Limitações das Soluções Atuais: A aplicação desktop, embora interativa, é standalone e não acessível via web (é necessário instalar/executar localmente). Já o protótipo web em Dash permite acesso via navegador, porém apresenta limitações: (a) Atualização em “quase” tempo real – o Dash envia updates a cada 0,5s, mas está limitado pelo loop do servidor e tráfego de imagens base64, o que pode introduzir latência e carga no servidor; (b) Interatividade limitada no front-end – Dash abstrai a interface, dificultando animações avançadas ou feedback instantâneo sem round-trip ao servidor; (c) Escalabilidade – o modelo Dash roda num único processo Python, com dificuldade para suportar múltiplos usuários simultâneos executando simulações intensivas; (d) Acoplamento – a lógica de simulação está diretamente embutida nos callbacks do Dash, tornando a arquitetura pouco modular (dificulta, por ex., substituir a UI sem tocar na lógica de simulação). Em suma, há espaço para uma arquitetura mais moderna que separe melhor as camadas e aproveite tecnologias web atuais para maior desempenho, interatividade e escalabilidade.
Requisitos para a Nova Aplicação Web
Com base na análise acima, a nova aplicação web deve atender aos seguintes requisitos principais:
Visualização Geoespacial em Tempo Real: Exibir a propagação do incêndio em tempo real sobre um mapa interativo. O usuário deve ver, sobre um mapa base (por exemplo, imagens ou terreno), as áreas pegando fogo, queimadas e intactas mudando dinamicamente. A solução deve suportar dados geoespaciais (GeoJSON) – por exemplo, a região de simulação definida pelo usuário – para alinhar a simulação a coordenadas reais. A visualização deve ser fluida, com atualizações frequentes (várias por segundo se possível) e representação visual clara (cores, opacidade, possivelmente animações de fogo).
Integração com APIs Externas (Dados Ambientais/Risco): A aplicação deve consumir serviços externos para enriquecer a simulação com dados do mundo real, como condições meteorológicas (temperatura, umidade, vento) ou índices de risco de incêndio. Por exemplo, ao definir a região de simulação, o sistema pode consultar uma API de clima para obter o índice de risco de fogo ou dados de seca para aquela área e período. Esses dados podem calibrar parâmetros do modelo (probabilidade de ignição espontânea, velocidade de propagação, eficácia dos bombeiros, etc.) ou simplesmente serem exibidos ao usuário como informação contextual. Exemplo: utilizar um serviço como o Ambee Wildfire API para obter dados de focos de incêndio ou risco em tempo real
getambee.com
. A integração deve ser robusta (com tratamento de erros de rede) e, se possível, assíncrona para não travar a simulação enquanto espera respostas.
Definição Interativa de Região (Desenho de Polígonos): O usuário deve conseguir definir no mapa a área de interesse para simulação desenhando polígonos ou outras formas. Essa funcionalidade – já vislumbrada no protótipo Dash – precisa estar presente de forma intuitiva na nova interface. Ao finalizar o desenho, a região será enviada ao backend (em formato GeoJSON) e usada para inicializar o modelo: por exemplo, recortando a grade de agentes ou mapeando o polígono para o grid interno. É importante que o usuário possa editar ou redesenhar a região facilmente, bem como talvez carregar arquivos GeoJSON próprios. Desenhar polígonos no mapa permite simular incêndios em qualquer área geográfica escolhida, aumentando a utilidade do sistema.
Compatibilidade com a Lógica de Agentes Existente: A nova solução deve reaproveitar ao máximo o modelo de simulação já implementado (EnvironmentModel, PatchAgent, FirefighterAgent, etc.), garantindo que os resultados permaneçam consistentes. Idealmente, a “engine” de simulação continuará sendo o código Python (Mesa) existente, para não reinvestir na lógica já testada. Isso implica expor o motor de simulação ao front-end via uma API, mantendo os agentes e regras (propagação do fogo, movimentação/ação dos bombeiros, atualização de estados) intactos. Quaisquer ajustes necessários devem ser mínimos – por exemplo, desacoplar a visualização do PySide6 ou remover suposições de ambiente desktop (como uso de QTimer). Essa compatibilidade reduz retrabalho e garante confiabilidade científica (os comportamentos complexos de fogo como sistema emergente são mantidos conforme o modelo original).
Tecnologias Modernas para Desempenho e Interatividade: Adotar ferramentas e arquiteturas atuais que elevem a experiência do usuário e a eficiência do sistema. Isso inclui atualizações em tempo real via WebSockets (em vez de requisições HTTP cíclicas) para diminuir latência e carga de rede, frameworks front-end modernos (como React, Vue ou Svelte) para criar uma SPA (Single-Page Application) rica em interatividade, componentes gráficos eficientes (como renderização via WebGL/canvas para muitos agentes), e animações/transições suaves (por exemplo, transição de cor quando células começam a queimar). A interface deve ser responsiva e dinâmica, dando feedback imediato às ações do usuário (como clicar para iniciar fogo ou pausar a simulação). Tecnologias como WebSockets abrem possibilidades de experiências em tempo real antes difíceis de obter no modelo Dash tradicional
medium.com
.
Arquitetura Modular e Escalável: A nova aplicação deve ser projetada em camadas separadas – tipicamente frontend, backend (API) e motor de simulação –, de modo a facilitar manutenção e permitir evolução de cada parte isoladamente. Uma separação clara cliente/servidor também torna a aplicação mais escalável: por exemplo, podendo instanciar múltiplos servidores de simulação em paralelo ou distribuir a carga entre frontends e backends. Essa modularidade favorece a reutilização (o motor de simulação poderia até ser usado em outros contextos, como linha de comando ou diferentes interfaces) e a colaboração em equipe (desenvolvedores web podem trabalhar no frontend sem entender todos os detalhes do modelo de fogo, e vice-versa). Em termos de implantação, uma arquitetura de microsserviços ou camadas desacopladas também permitiria hospedar componentes em infraestruturas distintas (por exemplo, frontend estático em CDN, backend em cloud auto-escalável). Em suma, o design deve separar a interface do usuário, a lógica de negócios da API e o engine de simulação. Isso é alinhado com arquiteturas web modernas, onde há um cliente leve e um servidor robusto – conforme exemplificado por trabalhos como o RWWSS (Real-time Web Wildfire Simulation System) que possui front-end (HTML/JS) separado do back-end e troca dados via JSON
cse.unr.edu
.
Estratégia Proposta para a Nova Arquitetura Web
Com os requisitos em mente, propõe-se a seguinte estratégia de arquitetura, incorporando inovações tecnológicas:
Visão Geral da Arquitetura (Camadas Frontend, Backend e Simulação)
A solução será estruturada em uma arquitetura cliente-servidor de três camadas principais:
Frontend (Client-Side Web App): Uma aplicação web executada no navegador do usuário, responsável pela interface gráfica e interações. Será uma SPA construída com tecnologias modernas (detalhadas adiante) e terá como principais funções: exibir o mapa interativo com a simulação, capturar ações do usuário (desenhar região, iniciar/pausar simulação, acionar cálculo de risco, etc.), e apresentar visualizações como gráficos e indicadores. O frontend comunicará com o backend via protocolos web – requisições HTTP/REST para operações pontuais (ex: solicitar início de simulação, obter dados estáticos) e WebSockets para receber atualizações em tempo real do estado da simulação.
Backend (Server-Side API): Um servidor web (provavelmente em Python, dado o reuso da lógica atual) que expõe APIs para controlar a simulação e integrarse com dados externos. O backend atua como intermediário entre o frontend e o motor de simulação: recebe do frontend as definições de região, comandos de início/pausa, etc., e orquestra o motor de simulação conforme essas entradas. Também faz as chamadas a APIs externas (por exemplo, consulta de risco ou clima) e retorna os resultados ao frontend. Crucialmente, o backend mantém uma conexão WebSocket aberta com cada cliente para envio contínuo de dados de simulação (frames do estado do incêndio, métricas a cada tick, etc.). Uma vez que a aplicação terá partes em tempo real, é recomendado usar um framework assíncrono e performático – FastAPI (sobre ASGI) é uma ótima escolha, oferecendo suporte nativo a WebSockets e alto desempenho em Python
medium.com
. Esse backend também pode incorporar mecanismos de broadcast (caso vários usuários assistam a mesma simulação) e autenticação básica se necessário.
Motor de Simulação (Simulation Engine): Componente que realiza o cálculo do modelo multiagente de incêndio. Aqui reside a lógica existente (Mesa model, agentes). Esse motor pode ser implementado como parte interna do backend (por exemplo, rodando em uma thread separada ou tarefa assíncrona dentro do servidor FastAPI) ou como um microsserviço isolado (um processo separado que o backend invoca ou com o qual se comunica). A decisão depende da complexidade: inicialmente, integrar no próprio backend (mantendo modularidade via boas abstrações de código) é mais simples. Em qualquer caso, o motor, ao ser acionado (setup da simulação), irá: inicializar um novo EnvironmentModel com parâmetros adequados (dimensões, densidade de vegetação, etc.), aplicar a região desenhada (pode-se mapear o polígono GeoJSON para o grid e marcar células fora dele como inativas, ou simplesmente considerar os limites para projeção coordenada como já feito no protótipo
file-bg8wxyzatzw7t2uqhhzfw4
file-bg8wxyzatzw7t2uqhhzfw4
), e então entrar em um loop de passos. A cada passo, o motor atualiza os estados dos agentes (por ex., espalha fogo, move bombeiros) e produz dados de saída (p. ex. lista de células queimando, porcentagem de área queimada, posições dos bombeiros). Esses dados de saída serão enviados em tempo real ao frontend via backend. O motor deve suportar comandos do backend, como pausar (congelar a evolução no estado atual), retomar, ou reinicializar.
Essa divisão garante independência entre as camadas. Conforme destacado em uma aplicação similar, separar front-end e back-end permite acesso amplo (qualquer dispositivo com navegador, sem instalação) e uso de tecnologias adequadas em cada lado

Frontend Interativo e Inovador
Para o frontend, propõe-se construir uma aplicação web single-page robusta, priorizando desempenho gráfico e experiência do usuário. Os pontos chave de implementação são:
Framework SPA: Utilizar um framework moderno como React (ou alternativamente Vue, Svelte). O React é recomendado pela maturidade e vasta coleção de bibliotecas. Isso permitirá criar uma aplicação modular, compondo elementos da UI como componentes reutilizáveis (por exemplo, um componente <MapaInterativo> para o mapa, <GraficoStatus> para o gráfico temporal, controles de botão, etc.). Além disso, frameworks SPA permitem atualizar partes da interface sem recarregar a página, essencial para animações em tempo real.
Mapa Interativo com Camadas Personalizadas: Incluir um mapa base (provavelmente de fonte OpenStreetMap ou similar) para dar contexto geográfico. Duas opções destacam-se:
Mapbox GL JS / MapLibre: biblioteca de mapas baseada em WebGL, capaz de renderizar milhares de objetos vetoriais de forma performática no navegador. Oferece renderização dinâmica e interativa, incluindo 3D e grande maleabilidade em estilo. Com Mapbox GL, é viável carregar a região de simulação como um layer vetorial (GeoJSON) e posteriormente atualizar as propriedades (cores) das feições rapidamente usando APIs de data-driven styling ou feature-state – técnica essa recomendada para visualizações em tempo real de dados vinculados a geometrias
mapbox.com
mapbox.com
. O Mapbox GL também possui extensões como mapbox-gl-draw para desenho e edição de polígonos diretamente no mapa (que poderíamos integrar via um wrapper React).
Leaflet: biblioteca de mapas 2D tradicional (usada no protótipo Dash via dash-leaflet). Tem a vantagem de simplicidade e inúmeros plugins (incluindo Leaflet.draw para polígonos). Em React, usaríamos React-Leaflet para integrar. Leaflet funciona bem para quantidades moderadas de marcadores/polígonos, mas para a simulação pode ser menos performático se muitas células forem atualizadas individualmente, já que não usa WebGL nativamente.
Dada a necessidade de desempenho (atualização frequente de ~13.500 células) e recursos visuais (animações, possivelmente camadas de calor), a opção Mapbox GL (ou sua versão open-source MapLibre GL) é atraente. Esta tecnologia permite mapas suaves e rápidos em múltiplas plataformas
mapbox.com
. Além disso, facilita trabalhar com dados geoespaciais no cliente, podendo, por exemplo, aplicar um shade semi-transparente sobre áreas queimadas ou até animar partículas para representar chamas, aproveitando o GPU. Entretanto, caso a curva de implementação seja um fator, poder-se-ia começar com Leaflet (que a equipe já experimentou via Dash) e evoluir para Mapbox se necessário.
Desenho de Polígonos: Incorporar na interface de mapa uma ferramenta de desenho para que o usuário selecione a região de simulação. Com Mapbox GL, usaríamos o plugin Mapbox GL Draw, que fornece modos de desenho/edição de polígonos. Com React-Leaflet, usaríamos o componente Leaflet.Draw (existe o pacote react-leaflet-draw). Em ambos os casos, o polígono resultante será convertido em GeoJSON e enviado ao backend. É importante fornecer feedback ao usuário – por exemplo, exibindo as coordenadas da área ou destacando o polígono selecionado. Também podemos permitir múltiplos polígonos ou formas (e.g., para simular focos múltiplos ou barreiras contrafogo), dependendo do escopo.
Visualização da Propagação em Tempo Real: No front-end, implementar a atualização visual do incêndio em sincronismo com os dados recebidos do servidor. Estratégias possíveis:
Atualização por Imagem Raster: Similar ao protótipo, o backend poderia enviar uma imagem (PNG) do estado do grid e o front-end simplesmente atualiza uma camada de imagem sobre o mapa. Essa abordagem é simples, porém não muito “inovadora” nem escalável (envio repetido de imagem base64 consome banda e não permite interação per-célula).
Atualização Vetorial/Gráfica no Cliente: Preferível é enviar dados estruturados (por exemplo, lista de células incendiando ou matriz de estados) e o cliente renderizar. Com Mapbox GL, poderíamos ter uma camada de círculos ou quadrados representando células incendiadas e atualizar suas posições/cores via WebGL. Alternativamente, usar uma camada canvas/WebGL customizada: por exemplo, a biblioteca deck.gl (da mesma família do React-Map-GL) tem um ScatterplotLayer ou até pode desenhar um grid se fornecermos as coordenadas, tirando proveito de GPU para centenas de pontos. Deck.gl suporta animações e pode facilmente re-renderizar milhares de pontos por frame.
Combinação híbrida: Outra ideia é utilizar feature-state do Mapbox: carregar inicialmente todas as células da grade como feições (por exemplo, um GeoJSON com pontos ou pequenos polígonos) e depois, a cada update, enviar apenas quais índices mudaram de estado e usar map.setFeatureState no cliente. Isso atualiza atributos (como cor) sem recarregar geometria. Essa técnica é mencionada pela Mapbox como altamente performática para joins de dados em tempo real a geometrias preexistentes

mapbox.com
.
Em qualquer caso, o front-end deve aplicar estilos claros: talvez células queimando destacadas em vermelho/orange vibrante, queimadas em cinza/preto, floresta intacta em verde, etc., similar às cores usadas atualmente (pode-se aproveitar a função EncontrarCor existente mapeando códigos para hex). Também podemos adicionar marcadores dinâmicos para agentes especiais – por exemplo, ícones de bombeiro se movendo conforme as coordenadas dos FirefighterAgent. Esses agentes podem ser representados por pequenos marcadores com ícones SVG (como no desktop havia um ícone de sirene para bombeiro técnico). A posição deles seria convertida de coordenadas da grade para lat/long dentro do polígono e atualizada em tempo real no mapa. A interface pode mostrar tooltips ao passar o mouse sobre esses agentes, exibindo seu status (combatendo fogo, indo para posição, etc.), tornando a simulação mais informativa. Por fim, para melhorar a percepção visual da propagação, pode-se empregar animações transitórias. Exemplo: quando uma célula passa de floresta para queimando, fazer um breve efeito de “piscar” ou aumentar opacidade, indicando ignição. Ou usar um efeito de difusão de calor (um gradiente) em volta de células queimando. Essas animações seriam implementadas via CSS ou canvas no front, sem impactar o motor de simulação (são apenas decorativas, baseadas em eventos recebidos).
Gráficos e Indicadores em Tempo Real: Além do mapa, o frontend exibirá gráficos como o de evolução da área queimada vs. não queimada no tempo, semelhante ao existente. Em vez de Plotly (que pode ser usado via React wrapper, mas é pesado), podemos optar por bibliotecas focadas em real-time charts como Chart.js, Recharts (para React) ou D3.js customizado. O gráfico receberá os pontos conforme o backend envia (por exemplo, arrays de burned_count e forest_count ao longo do tick). Esses gráficos devem atualizar incrementalmente (adicionar um ponto a cada novo tick) sem recomputar tudo, para manter performance. Indicadores numéricos, como percentual de área queimada, tempo simulado, número de focos ativos, etc., podem ser mostrados em um painel lateral ou rodapé.
Controles da UI: Incluir botões e painéis de controle para o usuário: Setup (iniciar nova simulação/resetar), Iniciar (play), Pausar, e possivelmente Step (avanço passo-a-passo) para depuração. Também um botão "Calcular Risco" que, após desenhar a região, faz a requisição ao backend e exibe o resultado (por exemplo, "Risco estimado: Alto (0.8)"). Esse resultado pode aparecer como um destaque textual ou até alterar a interface (ex: colorir a área com uma tonalidade indicando perigo). Além disso, pode-se fornecer sliders ou campos para ajustar parâmetros antes de iniciar – por exemplo, densidade da floresta, número de bombeiros, velocidade do vento inicial, etc., semelhantes aos inputs que a versão desktop possuía. Isso torna o sistema exploratório: o usuário pode testar cenários. Esses parâmetros seriam enviados ao backend quando a simulação é configurada.
Responsividade e UX: O design deve ser amigável e responsivo, funcionando bem em diferentes tamanhos de tela. Pode-se adotar um framework de UI (como Material-UI no React ou Bootstrap/Vue) para consistência visual. A interação via toque (em tablets, celulares) deve ser considerada – por exemplo, desenhar polígonos com gesto, clicar para iniciar fogo, etc., devem ter equivalentes táteis. A aplicação, se for leve e autônoma, também pode ser convertida em um PWA (Progressive Web App), permitindo que usuários instalem como app mobile/desktop e usem offline para simulações stand-alone (embora a funcionalidade de APIs externas exija conexão).
Resumidamente, o frontend proposto se assemelha a uma aplicação web geoespacial de última geração, combinando um mapa interativo, visualização de dados em tempo real e controles de simulação, tudo rodando fluidamente no navegador do usuário.
Backend e Motor de Simulação (Servidor de Dados e Cálculo)
No backend, a estratégia é construir um serviço robusto que coordene simulações e sirva dados ao frontend. Pontos principais:
Framework Backend: FastAPI em Python é indicado. Ele permite definir rotas REST de forma simples e também endpoints WebSocket. Sua natureza assíncrona é útil: por exemplo, podemos ter um loop de simulação rodando em background e usar asyncio/corrotinas para mandar dados ao cliente conforme prontos, sem bloquear outras requisições. Além disso, FastAPI fornece ótimo desempenho comparável a frameworks de baixo nível, e facilita escalabilidade horizontal (é compatível com servidores ASGI como Uvicorn/Gunicorn). Como citado em um guia, a combinação de um backend performático em FastAPI com um frontend React pode produzir aplicações em tempo real responsivas e escaláveis
medium.com
.
Gerenciamento de Simulação: Quando o frontend requisitar uma nova simulação (após usuário desenhar região e clicar "Setup" ou "Iniciar"), o backend irá instanciar o motor de simulação. Isso envolve:
Receber GeoJSON da região – via uma rota REST (por exemplo, POST em /simulation/region) ou via o próprio WebSocket (uma mensagem inicial contendo o polígono). O backend pode usar a biblioteca Shapely para converter o GeoJSON em um polígono e extrair bounding box e área, similar ao que o protótipo fazia

Inicializar Modelo – criar uma instância de EnvironmentModel (ou possivelmente uma subclasse adaptada) passando largura, altura e outros parâmetros. Aplicar Filtros da Região – após criar os patches, aplicar o polígono: por exemplo, marcar agentes PatchAgent fora do polígono como “fora de simulação” (poderíamos definir state="empty" e talvez cor diferenciada ou torná-los inertes). Integrar Dados Externos – neste ponto (ou logo após iniciar), o backend pode chamar APIs externas para obter parâmetros específicos daquela região e data. Loop de Simulação e WebSockets: Uma vez configurado, o backend inicia o loop de simulação. Em vez de depender de um dcc.Interval no cliente (como no Dash), aqui o servidor puxa os cordões: ele próprio itera os passos e envia atualizações via WebSocket. Poderá ser implementado de duas maneiras:
Abordagem threading: Iniciar um thread separado (ou processo via multiprocess) que executa while running: model.step(); enviar_estado(); sleep(dt) – onde dt poderia ser um pequeno intervalo para controlar a velocidade (ou até não usar sleep para rodar o mais rápido possível e simular tempo compressado, conforme necessidade). O WebSocket em FastAPI (ASGI) pode coexistir; precisaríamos sincronizar o envio de dados (FastAPI fornece utilitários thread-safe para enviar via websocket). Essa abordagem facilita usar a API Mesa síncrona.
Abordagem assíncrona pura: Se o modelo Mesa pudesse ser adaptado a async (não trivial pois atualmente ele itera agentes sincronicamente), poderíamos rodar passos em uma coro-tarefa. Mais simples é manter síncrono mas usar anyio.to_thread (utilitário do FastAPI) para executar model.step() em thread, retornando o estado, e então enviar pelo WebSocket async.
Em ambos casos, enquanto STATE.running = True, itera-se. Ao receber um comando de pausa (por ex., usuário clica Pausar, o frontend envia via REST ou WS um sinal), o loop pode suspender (esperar). O WebSocket permanece aberto, então ao retomar basta continuar enviando. Envio de dados: Em cada passo, o backend coleta as informações necessárias para o frontend. Isso pode ser:
Lista de células ativas: Por exemplo, extrair todas as células cujo estado mudou nesse tick (queimou ou apagou). Ou simplesmente todas as células burning e burned. Porém enviar milhares de pontos em JSON a cada 0.5s pode ser pesado. Uma otimização: enviar apenas diferenças (deltas) – como “célula (x,y) mudou de floresta para queimando”.
Imagem base64: O backend poderia reutilizar a função existente que gera uma imagem RGBA do grid

file-bg8wxyzatzw7t2uqhhzfw4
. Mas em vez de retornar via HTTP, enviaria o string base64 no WebSocket. Essa imagem seria então desenhada no cliente. É fácil de implementar mas menos eficiente do que mandar dados vetoriais, embora o tamanho da imagem seja pequeno (500x432 px escalada 4x no protótipo).
Estado agregado: Além do mapa, enviar valores agregados para gráficos: ex. número de queimadas, florestadas e tempo. No protótipo isso era guardado em listas STATE.burned, etc. Podemos enviar incrementalmente o novo ponto para alimentar o gráfico do cliente.
Posição de agentes móveis: Mandar coordenadas atualizadas dos bombeiros (e seu estado – se estão combatendo fogo ou movendo). Assim o frontend pode mover marcadores suavemente de A para B, talvez interpolando.
Eventos ou alertas: Ex.: “🔥 Fogo controlado” quando não há mais burning, ou “🚒 Bombeiro X ficou sem água”, para enriquecer a simulação. Esses podem ser exibidos no log de texto no frontend.
O canal WebSocket permite enviar todos esses dados em uma estrutura JSON organizada (por exemplo: { tick: 12, burned: 50, burningCells: [...], firefighters: [...], image: "data:image/png;..." }). No front-end, um handler JavaScript recebe o objeto e atualiza as respectivas partes da UI. Essa via de comunicação evita a necessidade de múltiplos endpoints REST sendo chamados continuamente, reduzindo a sobrecarga. Conforme apontado, essa estratégia de push em tempo real é muito eficiente e adequada para dashboards ao vivo

.
Gerenciamento de Múltiplas Sessões: Se a aplicação for multiusuário (vários usuários abrindo seu navegador e rodando simulações distintas), o backend deve isolar as sessões. Com FastAPI, podemos usar a conexão WebSocket individual para armazenar um objeto de modelo por usuário (por exemplo, um dicionário global que mapeia ws_client_id -> SimulationInstance). Cada WebSocket handler no servidor lida com um cliente. Assim, quando mensagens chegam do cliente (ex.: “ignite at lat,lon”), o servidor identifica qual modelo instanciar e chama model.start_fire_at(x,y)

 correspondente. Bibliotecas de gerenciamento de websockets (como fastapi-websocket-manager) facilitam broadcast e tracking de clientes. No nosso caso, broadcast não é tão necessário a não ser que quiséssemos vários usuários vendo a mesma simulação, o que é um caso especial (ex.: um professor transmitindo a simulação e alunos conectados assistindo). Nesse caso, poderíamos ter um room e replicar mensagens a todos os sockets naquela sala.
Persistência e Logs: Opcionalmente, o backend pode registrar os dados importantes – e.g., salvar o GeoJSON da região, parâmetros usados e resultados (curvas de queima) – em um banco de dados ou arquivo, para posterior análise. Isso permitiria replays ou comparação de cenários. Porém, se o foco é apenas simulação interativa, talvez não seja prioritário. Logging textual (como no QTextEdit log do desktop) pode ser enviado ao front-end ou console para debug.
Segurança: Como mínimo, implementar proteção para que chamadas à API externa de risco não exponham indevidamente o token (no protótipo ele é gerado no backend e não revelado ao cliente, o que é correto). No contexto de um app web público, poderíamos restringir ou autenticar o uso do endpoint de risco. FastAPI permite adicionar middleware de autenticação ou limitar origens (CORS) conforme necessário.

Tecnologias Inovadoras e Justificativas
Esta proposta incorpora diversas tecnologias modernas visando melhor desempenho e interatividade:
WebSockets para Tempo Real: Diferentemente do tradicional AJAX polling, os WebSockets permitem comunicação bidirecional persistente. Isso significa que o servidor pode enviar dados assim que estiverem prontos, e o cliente recebe instantaneamente, resultando em latência baixíssima e uso eficiente de rede. Conforme ressaltado em um estudo de caso, essa combinação de WebSockets no backend FastAPI com um frontend React viabiliza aplicações em tempo real com atualizações instantâneas e escalabilidade superior (menos overhead por atualização)
medium.com
. Em suma, WebSockets abrem um leque de recursos em tempo real – de animações ao vivo a colaboração multiusuário – impossíveis de atingir com Dash de forma performática.
Frameworks Frontend Modernos: O uso de React (ou Vue/Svelte) representa o estado-da-arte em desenvolvimento web, permitindo criar UIs complexas de forma declarativa e componível. Isso traz inovação em termos de mantainability (componentes reutilizáveis, unidirectional data flow) e performance (DOM virtual, updates parciais). Combinado a bibliotecas específicas (React-Leaflet, Mapbox GL JS, etc.), temos acesso a recursos avançados como mapas 3D, animações CSS-in-JS, gerenciamento de estado global (Redux ou Context API) – facilitando implementar, por exemplo, um indicador global de “simulação em andamento” acessível a múltiplos componentes.

Arquitetura Escalável: A separação de frontend e backend não só melhora manutenção, mas permite escalar independentemente. Por exemplo, se a simulação for computacionalmente pesada, podemos executar o motor em um serviço cloud potente ou em paralelo (várias instâncias FastAPI behind a load balancer), enquanto o frontend pode ser servido estaticamente via CDN. Podemos inclusive conceber múltiplos pods de simulação, alocando cada sessão de usuário a um pod separado, comunicando via WebSocket – alinhado a arquiteturas cloud-nativas. Essa escalabilidade garante que mesmo com muitos usuários simultâneos explorando cenários (ou um cenário muito grande) o sistema se mantenha responsivo. Manutenibilidade e Evolução: Usando tecnologias populares (React, FastAPI), garantimos longa durabilidade e comunidade de suporte. Adotar padrões REST e formatos como JSON/GeoJSON tornam o sistema interoperável – por exemplo, no futuro poderia-se criar um cliente móvel nativo que consome a mesma API para simulação. Em síntese, a estratégia propõe inovar ao migrar de um protótipo acoplado para uma arquitetura web moderna: frontend rico em SPA + backend assíncrono com WebSockets + motor ABM reutilizado, aproveitando ao máximo tecnologias web atuais (WebGL, APIs REST, cloud). Essa abordagem trará uma experiência de usuário muito mais imersiva e interativa, com visualização em tempo real de propagação de incêndios sobre mapas reais, possibilidade de ajuste de cenários com dados do mundo real, e uma base de código mais sustentável e expansível.

Melhoria significativa na experiência do usuário: visualização geográfica realista, atualização instantânea do estado do fogo e controle intuitivo da simulação.
